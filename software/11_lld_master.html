LOW-LEVEL DESIGN — COMPLETE INTERVIEW GUIDE

Zero to mastery: OOP pillars, SOLID, GOF design patterns, UML, object modeling, a step-by-step interview framework, and 10 fully-solved LLD problems with class diagrams + Java skeletons.

1. What is LLD & How the Round Works

Low-Level Design = turning a requirement into concrete classes, interfaces, and relationships — the blueprint that maps 1:1 to code. It's about object-oriented modeling and clean code, not databases or servers.

High-Level Design (HLD)Low-Level Design (LLD)
Question"How does the whole system fit together?""How do I model this one feature/module in code?"
ArtifactsComponents, servers, DBs, message queuesClasses, interfaces, UML class diagram
ScaleMillions of users, distributedSingle application, single process
Skills testedCapacity planning, trade-offsOOP, SOLID, design patterns, extensibility
What is an interviewer actually testing in an LLD round?

① Can you extract entities from an ambiguous prompt? ② Can you model relationships (has-a, is-a) correctly? ③ Do you apply SOLID & patterns to keep it extensible? ④ Is your code clean, readable, and testable? ⑤ Do you handle edge cases (invalid inputs, concurrency)?

Typical round format (45 min): 5 min clarify requirements → 10 min list entities/relationships → 10 min class diagram (on whiteboard/paper) → 15 min code the core classes → 5 min edge cases + trade-offs. Speak while you draw — narrate why you make each choice.

2. OOP Fundamentals (Refresh Before Patterns)

LLD is OOP applied. The 4 pillars are the vocabulary of every design conversation.

PillarIdeaHowExample
EncapsulationHide internal state; expose behaviorprivate fields + public methodsBankAccount.balance is private; only deposit()/withdraw() change it
InheritanceIs-a relationship, code reuseextendsCar extends Vehicle
PolymorphismSame interface, many behaviorsoverriding + interfacesall Payment impls implement pay() differently
AbstractionExpose contract, hide detailsinterface / abstract classPaymentProcessor interface; impls: CreditCard, UPI
Composition over inheritance — why is it a rule in interviews?

Deep inheritance (A extends B extends C) creates fragile coupling — change C, and A breaks silently. Composition (has-a: a Car has an Engine) is flexible, testable (mock the Engine), and swaps behavior at runtime. Favor composition unless there is a true is-a contract with shared logic.

Interface vs abstract class (interview classic): interface = pure contract, no state, multiple inheritance allowed, Java 8+ default methods; abstract class = can hold fields + constructor + shared code, single inheritance only. Rule of thumb: "is-a + shared code" → abstract; "can-do / capability" → interface.

3. SOLID Principles

SOLID is the grading rubric of every LLD interview. Memorize each with a "violation vs fix".

LetterNameViolation (Bad)Fix (Good)
SSingle ResponsibilityOne class does validation + DB + email + loggingOne class = one reason to change; split into validators, repository, notifier, logger
OOpen/ClosedAdding a new shape edits AreaCalculator with if-elseOpen for extension: Shape interface + each shape computes its own area()
LLiskov SubstitutionSquare extends Rectangle breaks setWidth() semanticsSubtypes must be substitutable for base type without breaking behavior
IInterface SegregationOne fat Worker interface with code() and manage()Split into Coder and Manager; classes implement only what they need
DDependency InversionHigh-level class calls a concrete MySQLRepoDepend on abstraction Repository interface; inject the concrete one
Quick spot-the-violation test

If a class has 3+ "and"s in its description ("handles payments AND notifications AND reports") it violates S. If switching DB means editing business logic, it violates D. If adding a feature means editing old code, it violates O.

5. UML Essentials

UML (Unified Modeling Language) = the drawing language for LLD. You must be able to draw and read a class diagram, and sketch a sequence diagram.

5.1 Class diagram notation

A class box has 3 compartments: Name | Attributes | Methods. Modifiers: + public, - private, # protected, _underlined = static.

5.2 Relationships (the part that gets you marks)

RelationshipArrowMeaningExample
Inheritance / is-aSolid line, hollow triangle → parentSubclassCar —▷ Vehicle
Interface realizationDashed line, hollow triangle → interfaceImplementsCar - - ▷ Drivable
AssociationPlain solid lineUses another class (has a reference)Doctor —— Patient
Aggregation (weak has-a)Solid line, hollow diamond → containerPart can outlive containerTeam ◇— Player (player survives team deletion)
Composition (strong has-a)Solid line, filled diamond → containerPart dies with containerHouse ◆— Room
DependencyDashed arrow → used thingUses only as method parameterReport - - > Printer

Multiplicity: 1, 0..1, *, 1..*, 0..* — put next to each end ("a ParkingLot has 1..* Spots").

Aggregation vs Composition — the safest interview answer

Composition = the part has no independent life ("a Room is meaningless without its House"). Aggregation = the part has its own life ("a Player still exists if the Team is disbanded"). When unsure, default to composition only if lifecycle is clearly coupled; otherwise aggregation or plain association.

5.3 Sequence diagram

Shows message flow over time for one use case. Lifelines are vertical dashed lines; messages are arrows between them; activation bars show when an object is busy. Example: Client → Controller.checkout() → OrderService.create() → PaymentService.pay() → DB.save() then return arrows back. Useful when an interviewer asks "walk me through the flow" — draw the happy path + one failure.

6. Object Modeling — Entities, Relationships, Multiplicity

The single most important LLD skill: reading an ambiguous prompt and extracting clean entities.

Step 1 — Nouns → Entities: circle every noun in the prompt. "Parking lot has floors, spots, vehicles, tickets, hourly rates, attendants." Candidate entities: ParkingLot, Floor, Spot, Vehicle, Ticket, RateCard.

Step 2 — Verbs → Behaviors: "park a car, exit, pay, reserve" → methods on entities (ParkingLot.park(), Spot.release(), Ticket.calculateAmount()).

Step 3 — Relationships & cardinality: ask "how many?" ParkingLot has 1..* Floor; Floor has 1..* Spot; Spot is assigned to 0..1 Vehicle (nullable — spot can be empty).

Step 4 — Separate is-a from has-a: Bike/Car/Truck are Vehicles (is-a). A ParkingLot has Floors (has-a). Don't force inheritance where has-a is natural.

Common modeling mistakes that kill interviews

① Modeling UI/DB as classes (no — classes are domain entities). ② Making everything a String — use enums (VehicleType.BIKE, SpotStatus.OCCUPIED). ③ God classes doing everything — violates S. ④ Forgetting nullability (a spot can be empty). ⑤ Duplicating data that should be a reference (store Vehicle id, not a copy).

7. The LLD Interview Framework (Follow This Every Time)

  1. Clarify requirements — read the prompt aloud, ask: scope, users, key operations, constraints (single/multi user, concurrency, memory vs DB). Write a 3-line summary.
  2. Extract entities — nouns of the problem. List them.
  3. Draw relationships — is-a and has-a, with multiplicity. This is your class diagram skeleton.
  4. Add methods to entities — verbs, with clear signatures + return types.
  5. Introduce interfaces where variability exists — payments, notifications, pricing, storage → Strategy pattern.
  6. Write the core classes in code — start with the domain model, then the orchestrator/service. Speak as you type.
  7. Edge cases — invalid input, empty collections, concurrency (two users take last item), nulls, overflow.
  8. Trade-offs & extensions — "how would you add a new requirement?" This is where SOLID + patterns earn marks.
The verbal script that works

"I'll model X as an entity because… It has Y and Z (aggregation), and A is a B (inheritance). I'll make this an interface because multiple implementations may vary — using Strategy keeps it Open/Closed. For concurrency I'll use a lock/atomic counter here." Narrating reasons converts your diagram into marks.

8. Solved LLD Problems (10)

P1 · Parking Lot

Requirements: multi-floor parking; spots of type (Bike/Car/Truck); assign nearest empty spot; ticket with entry/exit; fee by duration × type rate; no spot → reject; thread-safe.

Entities: ParkingLot(1..* Floor 1..* Spot), Vehicle (abstract: VehicleType), Ticket, FeeCalculator (Strategy).

enum VehicleType { BIKE, CAR, TRUCK }

class Vehicle { String regNo; VehicleType type; }

class Spot {
  String id; VehicleType type; SpotStatus status; // OCCUPIED / FREE
  synchronized boolean assign(Vehicle v);        // race-safe
}

class Floor { List<Spot> spots; Spot findNearestFree(VehicleType t); }

class Ticket { String id; Spot spot; LocalDateTime entryTime; }

class ParkingLot {
  List<Floor> floors;
  synchronized Ticket park(Vehicle v) {
    for (Floor f : floors) {
      Spot s = f.findNearestFree(v.type);
      if (s != null) { s.assign(v); return new Ticket(s); }
    }
    throw new RuntimeException("Lot full");
  }
  double exit(Ticket t, FeeCalculator calc) { return calc.calculate(t); }
}

interface FeeCalculator { double calculate(Ticket t); }
class PerHourFee implements FeeCalculator {
  Map<VehicleType, Double> rates = Map.of(BIKE, 10.0, CAR, 30.0, TRUCK, 50.0);
  public double calculate(Ticket t) {
    long h = Duration.between(t.entryTime, LocalDateTime.now()).toHours() + 1;
    return h * rates.get(t.spot.vehicleType);
  }
}

Edge cases: null vehicle, lot full, ticket not found, spot already occupied, free exit (grace period). Extension: parking on random-spot-allocation, electric charging spots → new VehicleType enum value = Open/Closed (enum switch is the only place to change).

P2 · Elevator

Requirements: N elevators; riders request floor from outside (directional) and inside (target); always move to the highest-priority request; prevent starvation; open/close with safety.

Entities: Elevator (state machine: IDLE/MOVING_UP/MOVING_DOWN/DOOR_OPEN), Button (ElevatorButton, FloorButton), Floor, ElevatorController (Scheduler strategy).

enum ElevatorState { IDLE, MOVING_UP, MOVING_DOWN, DOOR_OPEN }

class Elevator implements Runnable {
  int currentFloor; ElevatorState state = IDLE;
  TreeSet<Integer> upQueue = new TreeSet<>();
  TreeSet<Integer> downQueue = new TreeSet<>(Comparator.reverseOrder());
  void requestInside(int floor) { (floor > currentFloor ? upQueue : downQueue).add(floor); }
  synchronized void move() {
    if (state == IDLE && !upQueue.isEmpty()) state = MOVING_UP;
    if (state == MOVING_UP) { currentFloor++; if (upQueue.remove(currentFloor)) stopAndOpen(); }
    if (upQueue.isEmpty() && downQueue.isEmpty()) state = IDLE;
  }
  void stopAndOpen() { state = DOOR_OPEN; /* open door, wait, close */ }
}

class ElevatorController {
  List<Elevator> elevators;
  Elevator findBest(int floor) {
    // Strategy: closest idle elevator, or one already passing in same direction
    return elevators.stream().min(Comparator.comparingInt(e -> Math.abs(e.currentFloor - floor))).get();
  }
  void handleExternalRequest(int floor, Direction dir) { findBest(floor).requestInside(floor); }
}

Design decisions: two TreeSets keep it O(log n) per request and give direction behavior free. Look-ahead scheduling (serve in same direction first) is what real elevators do. Edge cases: same-floor request, both queues empty, multiple elevators (distribute, avoid two elevators answering the same call), last floor bounds.

P3 · Library Management System

Requirements: members borrow/return books; catalog search by title/author; book has copies (some available); overdue tracking + fine; limits per member (e.g. 5 books).

Entities: Book (BookDetails + copies), Member, BookCopy (status AVAILABLE/BORROWED/RESERVED), Library, Loan (member, copy, dueDate), FineCalculator.

class BookCopy { String id; Book book; CopyStatus status; }

class Book {
  String title; List<String> authors; String isbn;
  List<BookCopy> copies = new ArrayList<>();
  synchronized BookCopy borrowAvailable() {
    return copies.stream().filter(c -> c.status == AVAILABLE).findFirst().orElse(null);
  }
}

class Member {
  String id; String name; List<Loan> loans = new ArrayList<>();
  static final int MAX_LOANS = 5;
  boolean canBorrow() { return loans.size() < MAX_LOANS; }
}

class Library {
  Map<String, Book> booksByIsbn;
  synchronized Loan borrow(Member m, Book b) {
    if (!m.canBorrow()) throw new RuntimeException("Loan limit reached");
    BookCopy c = b.borrowAvailable();
    if (c == null) throw new RuntimeException("No available copy");
    c.status = BORROWED;
    Loan loan = new Loan(m, c, LocalDate.now().plusDays(14));
    m.loans.add(loan);
    return loan;
  }
  double returnBook(Member m, Loan l) {
    l.copy.status = AVAILABLE; m.loans.remove(l);
    long overdue = ChronoUnit.DAYS.between(l.dueDate, LocalDate.now());
    return overdue > 0 ? overdue * 5.0 : 0;
  }
}

Patterns used: Book has BookCopy (composition) — copies share book metadata (avoids duplication). Reserve system is the classic follow-up (copy RESERVED until the reserving member takes it). Edge cases: returning someone else's loan, renew, book not found, concurrent borrowing of the last copy (synchronized handles it).

P4 · Vending Machine

Requirements: items in slots (code, price, qty); insert coins/notes; select item; dispense + change; cancel refunds; only one transaction at a time.

This is THE state-machine problem. Entities: VendingMachine, State (interface), Item, Inventory, Coin enum.

enum Coin { PENNY(1), DIME(10), NICKEL(5), QUARTER(25); int value; Coin(int v){value=v;} }

class Item { String code; String name; double price; }

interface MachineState {
  MachineState insertCoin(Coin c, VendingMachine vm);
  MachineState selectItem(String code, VendingMachine vm);
  MachineState dispense(VendingMachine vm);
  MachineState cancel(VendingMachine vm);
}

class IdleState implements MachineState {           // no coin inserted yet
  public MachineState insertCoin(Coin c, VendingMachine vm) {
    vm.accumulate(c.value);
    return vm.hasSelection ? new SelectionMadeState() : new HasMoneyState();
  }
  public MachineState selectItem(String code, VendingMachine vm) { vm.select(code); return this; }
  public MachineState dispense(VendingMachine vm) { throw new IllegalStateException(); }
  public MachineState cancel(VendingMachine vm) { return this; }
}
// HasMoneyState: accumulates coins; if enough -> DispenseState
// DispenseState: decrement qty, give change, reset -> IdleState

class VendingMachine {
  MachineState state = new IdleState();
  Inventory inventory; double balance; double collectedMoney; String selectedCode;
  void insertCoin(Coin c) { state = state.insertCoin(c, this); }
  void selectItem(String code) { state = state.selectItem(code, this); }
  void pressDispense() { state = state.dispense(this); }
}

Why the State pattern: each state's allowed actions are explicit; invalid actions throw instead of if-else sprawl; adding a "Maintenance" state = one new class. Edge cases: insufficient money, item sold out, exact-change-only machine, coin reject, timeout between coins.

P5 · Splitwise (Expense Sharing)

Requirements: users; groups; add expense (equal or exact/percent split); show balances between users; settle debts; net balances should be minimized.

Entities: User, Group, Expense (paidBy, splitType), Split (per-user amount owed), BalanceSheet, SplitStrategy.

enum SplitType { EQUAL, EXACT, PERCENT }

interface SplitStrategy { List<Split> split(Expense e, List<Double> values); }

class EqualSplit implements SplitStrategy {
  public List<Split> split(Expense e, List<Double> values) {
    double per = e.amount / e.participants.size();
    return e.participants.stream().map(u -> new Split(u, per)).toList();
  }
}

class BalanceSheet {
  Map<String, Map<String, Double>> net;   // from -> to -> amount
  void record(Expense e) {
    double paid = e.paidBy;
    for (Split s : e.splits) {
      if (s.user == e.payer) continue;
      addEdge(e.payer, s.user, s.amount);  // payer is owed
    }
  }
  // Settle: build a min-flow / greedy two-pointer:
  // 1) net[user] = sum(owed) - sum(lent)
  // 2) sort debtors & creditors; while both non-empty, transfer min
}

Key interview point — minimizing transactions: after netting everyone, use a two-pointer greedy: order by net amount, match biggest debtor to biggest creditor, transfer min(debt, credit) → O(n) transactions (close to optimal). Edge cases: self-payment, rounding in percent splits (assign remainder to last user), user not in group, expense with 0 participants.

P6 · ATM Machine

Requirements: card → PIN verify → menu: balance / deposit / withdraw / change PIN; dispense denominations (100/500/2000); insufficient funds or notes → reject; session timeout.

Entities: ATM, Card, Account, BankDatabase, CashDispenser, ATMState (state machine again: Idle→CardInserted→PinEntered→Transaction→EjectingCard).

class CashDispenser {
  Map<Integer, Integer> notes;  // denomination -> count
  synchronized void dispense(double amount) {   // greedy largest-first
    int remaining = (int) amount;
    for (int denom : new int[]{2000, 500, 100}) {
      int need = remaining / denom;
      int give = Math.min(need, notes.getOrDefault(denom, 0));
      notes.put(denom, notes.get(denom) - give);
      remaining -= give * denom;
    }
    if (remaining != 0) throw new RuntimeException("Cannot dispense exact amount");
  }
}

class Account {
  String number; double balance; String pinHash;
  boolean validatePin(String pin) { return hash(pin).equals(pinHash); }
  synchronized void withdraw(double amt) {
    if (amt > balance) throw new RuntimeException("Insufficient funds");
    balance -= amt;
  }
}

class ATM {
  CashDispenser dispenser; BankDatabase db; ATMState state = new IdleState();
  void insertCard(Card c) { state = state.insertCard(c, this); }
  void enterPin(String pin) { state = state.enterPin(pin, this); }
  void withdraw(double amt) {
    state.withdraw(amt, this);   // validate -> account.withdraw -> dispenser.dispense
    dispenser.dispense(amt);
  }
}

Critical ordering: account.balance check → dispense notes → debit account. Dispense after debit loses money on machine failure; dispense before debit risks inconsistency — use a transaction. Edge cases: wrong PIN (3 attempts → card retained), withdrawal > daily limit, amount not a multiple of 100, zero balance, deposit validation.

P7 · Movie Ticket Booking

Requirements: shows at theatres; select show → seat layout; pick seats → 5-min payment hold → book; concurrent seat selection must not double-book; cancellations release seats.

Entities: Theatre, Screen, Show, Seat, Booking (status: PENDING/PAID/CANCELLED), PaymentService, SeatLockService.

class Show {
  Screen screen; LocalDateTime start; Map<String, Seat> seats;  // "A1", "A2"
}

class Seat {
  String id; SeatStatus status;   // AVAILABLE, LOCKED, BOOKED
  synchronized boolean lock(User u) {
    if (status != AVAILABLE) return false;
    status = LOCKED; return true;
  }
  synchronized void book() { if (status == LOCKED) status = BOOKED; }
}

class BookingService {
  Map<String, Booking> bookings;
  synchronized Booking createBooking(Show s, List<String> seatIds, User u) {
    for (String id : seatIds) if (!s.seats.get(id).lock(u)) throw new RuntimeException("Seat taken");
    Booking b = new Booking(s, u, seatIds); b.status = PENDING;
    scheduleExpiry(b, 5, MINUTES);   // after 5 min, release lock if unpaid
    return b;
  }
  synchronized void confirm(Booking b, PaymentService ps) {
    ps.charge(b.total); b.status = PAID;
    b.seatIds.forEach(id -> b.show.seats.get(id).book());
  }
  synchronized void cancel(Booking b) {
    b.seatIds.forEach(id -> b.show.seats.get(id).status = AVAILABLE);
    b.status = CANCELLED; refund();
  }
}

Concurrency answer: per-seat lock + synchronized on booking guarantees two users never hold the same seat. Real systems use Redis SETNX/locks with TTL — mention that. Extensions: seat categories (Premium/Standard) with price multipliers (Strategy), waitlist, partial seat release. Edge cases: expired booking being paid (reject), seat already locked by self, duplicate seat in request, show already started.

P8 · Restaurant / Food Delivery

Requirements: menu items (veg/non-veg); cart; place order → track states (PLACED→PREPARING→READY→OUT_FOR_DELIVERY→DELIVERED); notifications on state change; cancel before preparation.

Entities: Restaurant, Menu, MenuItem, Cart, Order, OrderState (State pattern — perfect fit), NotificationService (Observer).

interface OrderState {
  OrderState next();        // PLACED->PREPARING->...->DELIVERED
  boolean canCancel();
  String name();
}
class PlacedState implements OrderState {
  public OrderState next() { return new PreparingState(); }
  public boolean canCancel() { return true; }
}
// ... Preparing (cancel=false), Ready, OutForDelivery, Delivered (terminal)

class Order {
  OrderState state = new PlacedState();
  List<OrderItem> items; double total;
  void advance() {
    state = state.next();
    notifier.notify(NotificationType.toMessage(state));
  }
  void cancel() {
    if (!state.canCancel()) throw new RuntimeException("Cannot cancel now");
    state = new CancelledState();
  }
}

interface NotificationChannel { void send(String msg); }
class EmailChannel implements NotificationChannel { ... }
class SmsChannel implements NotificationChannel { ... }
class NotificationService {          // Observer: subscribes channels to order events
  List<NotificationChannel> channels;
  void notify(String msg) { channels.forEach(c -> c.send(msg)); }
}

Patterns showcase: State (order lifecycle), Observer/Strategy (notification channels), Factory (channels built by type). Edge cases: cancel an already-paid order (refund path), advance past delivered, empty cart, duplicate items in cart (merge quantities).

P9 · Tic-Tac-Toe

Requirements: two players (X/O), 3×3 board, alternate turns, detect win/draw, prevent moves on filled cells, replay + game history for extensions.

Entities: Board, Player (enum or class), Game (orchestrator), Move, WinChecker (Strategy — supports N×N).

enum Mark { X, O, EMPTY }

class Board {
  Mark[][] grid = new Mark[3][3];
  boolean place(int r, int c, Mark m) {
    if (grid[r][c] != EMPTY) return false;
    grid[r][c] = m; return true;
  }
}

interface WinChecker { boolean hasWon(Board b, Mark m, int lastR, int lastC); }
class BoardWinChecker implements WinChecker {
  public boolean hasWon(Board b, Mark m, int r, int c) {
    boolean row = true, col = true, diag = r == c, anti = r + c == 2;
    for (int i = 0; i < 3; i++) {
      row &= b.grid[r][i] == m; col &= b.grid[i][c] == m;
      diag &= b.grid[i][i] == m; anti &= b.grid[i][2 - i] == m;
    }
    return row || col || diag || anti;
  }
}

class Game {
  Board board; Player current = Player.X; WinChecker checker;
  GameStatus play(int r, int c) {
    if (board.place(r, c, current.mark)) {
      if (checker.hasWon(board, current.mark, r, c)) return current == Player.X ? X_WINS : O_WINS;
      if (movesPlayed() == 9) return DRAW;
      current = other(current); return ONGOING;
    }
    throw new IllegalArgumentException("Cell occupied");
  }
}

Why WinChecker is an interface: generalize to 4-in-a-row / N×N Connect-4 later without touching Game (Open/Closed). Edge cases: out-of-bounds, cell occupied, game already over, move after win, draw detection ordering (check win before draw).

P10 · Logging Framework

Requirements: log levels (DEBUG/INFO/WARN/ERROR); multiple appenders (console/file); message formatting; thread-safe; configurable level filter; Singleton facade.

Patterns: Singleton + Decorator + Chain of Responsibility + Factory. This one question can showcase 4 patterns.

enum LogLevel { DEBUG(0), INFO(1), WARN(2), ERROR(3); int weight; }

abstract class Logger {                     // Chain of Responsibility
  protected LogLevel level;
  protected Logger next;                    // e.g. DEBUG -> INFO -> WARN -> ERROR
  Logger setNext(Logger n) { this.next = n; return this; }
  void log(LogLevel l, String msg) {
    if (l.weight >= level.weight) write(l, msg);
    if (next != null) next.log(l, msg);
  }
  abstract void write(LogLevel l, String msg);
}
class ConsoleLogger extends Logger { void write(LogLevel l, String msg) { System.out.println(ts() + " " + l + " " + msg); } }
class FileLogger extends Logger { void write(LogLevel l, String msg) { fileWriter.append(ts() + " " + l + " " + msg + "\n"); } }

class LogManager {                          // Singleton
  private static volatile LogManager instance;
  Logger root;
  static LogManager getInstance() {
    if (instance == null) synchronized (LogManager.class) { if (instance == null) instance = new LogManager(); }
    return instance;
  }
  void info(String m) { root.log(LogLevel.INFO, m); }
}

Concurrency: message formatting with ThreadLocal timestamp + synchronized write() on appenders to avoid interleaved lines. Extensions: JSON formatter (Decorator), async buffer queue (Producer–Consumer), pattern-layout config. Edge cases: null message, writing to closed file, level filtering at root vs per-appender.

9. LLD Quick Revision Flashcards

What are the 4 pillars of OOP?

Encapsulation (hide state), Inheritance (is-a reuse), Polymorphism (one contract, many behaviors), Abstraction (expose contract, hide detail).

Composition over inheritance — when do you actually use inheritance?

Only when there is a true is-a relationship with shared concrete behavior. Otherwise use composition (has-a) which is more flexible and testable.

Which pattern makes adding a new payment method require zero changes to Order?

Strategy — Order depends on a PaymentStrategy interface; new methods implement the interface (Open/Closed).

Aggregation vs Composition?

Aggregation = part has independent life (Team◇—Player). Composition = part dies with container (House◆—Room).

How do you prevent two users from booking the same movie seat?

Per-seat lock: synchronized lock() on the seat object (or Redis SETNX with TTL in a real system) so only one user can transition AVAILABLE→LOCKED.

Name the state machine pattern and when it fits.

State pattern. When an object's behavior depends on its state and there are many transitions — Vending machine, Order lifecycle, Elevator, ATM.

What is a God class and why is it bad?

A class that handles far too many responsibilities — violates Single Responsibility; hard to test, change, and understand. Split into focused classes + orchestrate.

Class diagram relationship arrows quick recall?

Solid hollow-triangle = inheritance; dashed hollow-triangle = implements; solid line = association; hollow diamond = aggregation; filled diamond = composition; dashed arrow = dependency.

What does multiplicity "1..*" mean?

One-to-many: the referenced object appears at least once, unbounded above (e.g. a Floor holds 1..* Spots).

Interview golden rule for LLD?

Narrate WHY you model each class, relationship, interface, and pattern. The reasons are worth more than the code itself.
