2. Top SQL Drills

SQL is the most critical technical screening filter. Expect live coding where you share your screen and write queries from scratch.

Q1. Explain the difference between ROW_NUMBER(), RANK(), and DENSE_RANK() with an illustrative schema.

Approach: Write a query showing the behavior when values are identical (ties).

-- Let's assume we have identical salaries: 100, 100, 80
SELECT 
  employee_id, salary,
  ROW_NUMBER() OVER (ORDER BY salary DESC) as row_num,   -- 1, 2, 3
  RANK() OVER (ORDER BY salary DESC) as rnk,             -- 1, 1, 3 (skips rank 2)
  DENSE_RANK() OVER (ORDER BY salary DESC) as dense_rnk  -- 1, 1, 2 (no gaps)
FROM employees;
Q2. Calculate Monthly Active Users (MAU) and month-over-month user retention.

Concept: Self-join on user activity tables offset by 1 month.

WITH MonthlyActive AS (
  SELECT DISTINCT 
    user_id, 
    DATE_TRUNC('month', login_time) as login_month
  FROM user_logins
)
SELECT 
  curr.login_month as current_month,
  COUNT(DISTINCT curr.user_id) as active_users,
  COUNT(DISTINCT prev.user_id) as retained_users,
  ROUND(COUNT(DISTINCT prev.user_id) * 100.0 / COUNT(DISTINCT curr.user_id), 2) as retention_percentage
FROM MonthlyActive curr
LEFT JOIN MonthlyActive prev 
  ON curr.user_id = prev.user_id 
  AND curr.login_month = prev.login_month + INTERVAL '1 month'
GROUP BY curr.login_month;
Q3. Explain what happens during Joins on columns containing NULL values.

Trap: NULL = NULL evaluates to UNKNOWN (not TRUE). Joining tables on columns where matches are null will drop those rows. To count or match nulls, you must write explicit null checks (e.g. A.id = B.id OR (A.id IS NULL AND B.id IS NULL)) or use COALESCE.

3. Python for Data Engineering

Tredence values the ability to write clean, memory-efficient code. You will be asked about basic script composition, grouping, and generators.

Q1. Writing a memory-efficient file processor (Generators).

What if a file is 20GB and your RAM is 8GB? Use generators to process row-by-row without loading the full file in memory.

def read_large_log(file_path):
    with open(file_path, "r", encoding="utf-8") as file:
        for line in file:
            yield line.strip()

# Usage (only reads one line at a time):
for raw_log in read_large_log("massive_logs.csv"):
    if "ERROR" in raw_log:
        process_error(raw_log)
Q2. Implement a Python function to group transactions and compute total metrics without using external libraries (e.g. Pandas).

Task: Group list of dictionaries `{'user': str, 'amount': float}` by user and sum balances.

def aggregate_transactions(transactions):
    summary = {}
    for tx in transactions:
        user = tx['user']
        amount = tx['amount']
        if user not in summary:
            summary[user] = {'count': 0, 'total': 0.0}
        summary[user]['count'] += 1
        summary[user]['total'] += amount
    return summary

4. Data Engineering Theory Checklist

Prepare for theory questions concerning data modeling and storage structures:

  • OLTP vs OLAP: OLTP (Online Transaction Processing) is optimized for fast, write-heavy, row-oriented operations (e.g., PostgreSQL for transactions). OLAP (Online Analytical Processing) is optimized for read-heavy, column-oriented, analytical queries (e.g., Snowflake, Redshift for data warehouses).
  • Star Schema vs Snowflake Schema:
    • Star Schema: Fact tables connect directly to denormalized dimension tables. Fast queries, redundant storage.
    • Snowflake Schema: Dimension tables are normalized (split into sub-tables). Saves space, but adds query complexity due to joins.
  • ETL vs ELT:
    • ETL (Extract, Transform, Load): Data is transformed before reaching target storage. Good for security/anonymization, but slower.
    • ELT (Extract, Load, Transform): Data is loaded directly to a cloud data lake/warehouse, using storage compute to transform it later. Fast and scalable.

5. Case Studies & Guesstimates

These questions evaluate your logical structuring and estimation skills rather than getting a perfectly accurate number.

The Golden Rule for Guesstimates: Always structure your formula first! State assumptions clearly, choose round numbers, and sanity-check your final output.
Guesstimate 1: Estimate the daily revenue of a Starbucks in Outer Ring Road, Bangalore.

Structuring Strategy:

  1. Divide by Hours of Operation (e.g., 7 AM to 11 PM = 16 hours). Split into peak hours (8 AM - 11 AM, 4 PM - 7 PM = 6 hours) and non-peak hours (10 hours).
  2. State order rate assumptions:
    • Peak: 1 order every 30 seconds = 120 orders/hour.
    • Non-peak: 1 order every 3 minutes = 20 orders/hour.
  3. Calculate Total Orders: (6 * 120) + (10 * 20) = 720 + 200 = 920 orders/day.
  4. Average Order Value (AOV): Coffee + side snacks ≈ ₹300.
  5. Estimated Revenue: 920 orders * ₹300 = ₹2,76,000/day.
Guesstimate 2: How many tennis balls fit inside a Boeing 747?

Structuring Strategy:

  1. Estimate Volume of Boeing 747: treat it as a cylinder. Length ≈ 70m, Radius ≈ 3m. Volume = π * r² * h ≈ 3 * 9 * 70 ≈ 1900 m³.
  2. Adjust for interior (seats, overhead, cargo): Assume 50% usable empty volume ≈ 950 m³.
  3. Estimate Volume of a Tennis Ball: Radius ≈ 3.3 cm (0.033m). Volume = 4/3 * π * r³ ≈ 4 * (0.033)³ ≈ 0.00015 m³.
  4. Account for packing coefficient (empty air gaps): Random packing allows about 64% bubble efficiency. Usable volume = 950 * 0.64 ≈ 600 m³.
  5. Final division: 600 / 0.00015 = 4,000,000 tennis balls.

6. Behavioral & Communication (STAR Method)

Speak slowly and structure your thoughts. Here are 3 common scenarios Tredence asks, mapped to the STAR method:

S1: "Tell me about a time you had to deal with ambiguous requirements."
  • S (Situation): For my final year project, we had to build a cloud pipeline but the client details kept changing.
  • T (Task): I needed to freeze requirements and design a flexible, scalable architecture.
  • A (Action): I scheduled a clarify call, presented a mock dashboard to align expectations, and built a modular pipeline so schema updates wouldn't break it.
  • R (Result): We delivered ahead of schedule and the client approved the final system without rework.
S2: "How would you handle a situation where a client is unhappy with your dashboard/data model?"
  • S (Situation): A client complained that our data pipeline updates were too slow.
  • T (Task): I had to resolve the bottleneck under pressure of an impending business review.
  • A (Action): Instead of being defensive, I checked logs, identified joining traps on unindexed fields, converted nested queries to temp tables, and added comments detailing changes.
  • R (Result): Execution speed improved by 60%, and we gained the client's long-term trust.
