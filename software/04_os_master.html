OPERATING SYSTEMS — COMPLETE INTERVIEW GUIDE

Mechanism-level explanations: process/thread, scheduling, deadlock, synchronization, memory, IPC, syscalls + full flashcard set.

1. Process vs Thread

ProcessThread
MemoryOwn independent address spaceShares heap+code+data, own stack+registers
CommunicationIPC (pipes, sockets, shmem)Shared memory (needs locks)
Crash isolationHigh — one crash doesn't affect othersLow — one thread crash kills process
Context switchExpensive (TLB flush, page tables)Cheap (registers + stack only)
CreationSlow (fork + exec)Fast (pthread_create)
OwnsPCB, page tables, file tableStack + registers; shares rest
Which to choose?

Threads when work units must share state directly and cheaply (a kv_store) — cost is explicit synchronization. Processes when isolation matters more than sharing (a shell's independent commands) — a crash shouldn't take the shell down.

2. Process States & Context Switching

5-state model: New → Ready → Running → Waiting/Blocked → Terminated.

StateMeaning
Newbeing created
Readyloaded, waiting for CPU — could run immediately
Runningexecuting on a CPU core
Waiting/Blockedwaiting on event (I/O, lock) — can't run even with CPU
Terminateddone — zombie until parent reaps (wait())
What moves Running → Ready (not Blocked)?

Preemption — timer interrupt (time slice expired) or higher-priority process becomes ready; the OS forcibly takes the CPU. Blocked happens because the process itself requested something it must wait for (e.g. read() with no data).

Is a thread context switch cheaper than a process switch? Why?

Yes — thread switch saves/restores registers + stack pointer but shares the address space, so no page-table switch or TLB flush. Process switch requires both.

Context switch steps: save registers → PCB → update state → move to queue → schedule next → load its PCB → restore registers → flush TLB → run at PC.

3. PCB — What Gets Saved

Process Control Block = the kernel's record for a process: PID, state, CPU registers, program counter, stack pointer, memory info (page table pointers), open file descriptor table, scheduling info (priority, queue pointers).

4. CPU Scheduling Algorithms

What is "aging" and what does it solve?

Aging gradually increases a waiting process's priority — a direct fix for starvation in priority scheduling, guaranteeing even low-priority processes eventually run.

Formulas: Turnaround = completion − arrival · Waiting = turnaround − burst · Response = first CPU allocation − arrival.
Quantum choice: q→∞ = FCFS; q→0 = too many switches; ideal ≈ slightly larger than typical burst (10–100 ms).

5. Concurrency & Synchronization

Race conditions & critical sections

A race condition occurs when correctness depends on the relative timing of concurrent operations (≥2 threads access shared data, ≥1 write, no synchronization). The critical section is the code accessing the shared resource.

Three requirements of a correct critical-section solution:

① Mutual exclusion — only one thread in at a time. ② Progress — if CS is free, a wanting thread must be able to enter. ③ Bounded waiting — a limit on how many others can enter before a waiting thread gets its turn.

Mutex vs Semaphore vs Monitor

MutexSemaphoreMonitor
Purposemutual exclusion (binary lock)signaling / N resourceslock + condition vars bundle
Ownershiponly locker unlocksany thread can signalimplicit
Valuelocked/unlockedinteger counter (binary or N)implicit
Priority inheritanceyes (RTOS)usually no—
Example where a semaphore fits and a mutex doesn't?

A connection pool allowing at most 5 concurrent DB connections — a counting semaphore initialized to 5 lets exactly 5 threads proceed, blocking the 6th. A mutex only models "1 at a time".

  • Producer-Consumer: mutex (protect buffer) + empty(N) + full(0) semaphores.
  • Readers-Writers: first = reader preference (writer starves); second = writer preference.
  • Spinlock: busy-wait loop — use when the critical section is very short (saves context-switch cost).

6. Deadlock

Four necessary conditions (ALL must hold simultaneously)

ConditionMeaning
① Mutual Exclusionresource held in non-shareable mode
② Hold & Waitholding one, waiting to acquire others
③ No Preemptionresources can't be forcibly taken
④ Circular Waitcycle: P1 waits for P2's resource, P2 waits for P1's
// Thread 1:            // Thread 2:
lock(mutexA);            lock(mutexB);
lock(mutexB);   // waits  lock(mutexA);   // waits → deadlock
How to fix the 2-lock deadlock?

Enforce consistent global lock ordering — always acquire mutexA before mutexB in EVERY thread. Circular wait becomes structurally impossible, breaking condition ④.

Prevention / Avoidance / Detection

StrategyIdea
Preventionbreak one of the 4 conditions (spooling, request-all-at-once, preempt, total ordering)
AvoidanceBanker's algorithm — only grant if a safe sequence exists
Detection + Recoveryallow it, check for cycles in resource-allocation graph, recover by preemption/kill

Deadlock vs Starvation vs Livelock vs Contention

  • Deadlock — permanent cycle of mutual waiting; none can ever proceed.
  • Starvation — CAN run but keeps getting passed over (no cycle, just unfairness).
  • Livelock — actively changing state but making no progress (two people dodging each other in a hallway).
  • Contention — threads competing for a lock → serialization/queueing (a performance issue, NOT a correctness bug).

Gotcha: every client thread serializing on one global mutex is contention, not deadlock — every thread WILL eventually get the lock.

7. Memory Management

Paging vs Segmentation

PagingSegmentation
Unitfixed-size pages/framesvariable logical segments (code, stack, heap, data)
Fragmentationinternal (wasted inside page)external (gaps between segments)
Hardwarepage table + TLBsegment table

Page faults

A page fault occurs when a process accesses a page not currently mapped to a frame. NOT always an error: a "minor" fault (page exists, not yet mapped — first access) is normal demand paging. A "major" fault requiring an actual disk read is expensive.

Page replacement

AlgorithmIdeaWeakness
FIFOevict oldest-loadedBelady's anomaly — more frames can cause MORE faults
LRUevict least-recently-usedexpensive to track exactly in hardware
Optimalevict farthest-in-futureneeds future knowledge — theoretical benchmark
Clock (2nd chance)LRU approximation w/ reference bitless precise, cheaper

TLB, Thrashing, Copy-on-Write

  • TLB — small fast cache of recent virtual→physical translations. Hit = 1 cycle; miss = 10–100 (page walk). Process switch flushes it → that's why process context switches cost more than thread switches. Reach = TLB size × page size; huge pages increase reach.
  • Thrashing — more time swapping than executing (too many processes, too few frames). Detect: spiking fault rate with dropping CPU utilization. Mitigate: reduce degree of multiprogramming / working-set model.
  • Copy-on-Write — fork() shares read-only pages; first write triggers a fault that copies just that page → fork() is fast.
  • Virtual memory benefits: isolation, abstraction, sharing, demand paging.

8. IPC — Inter-Process Communication

MechanismIdea
Pipesunidirectional byte stream, parent-child
Named pipes (FIFOs)pipe with a filesystem name — unrelated processes
Shared memoryfastest — same physical RAM mapped into both processes; needs explicit synchronization
Message queueskernel-managed queue of discrete messages
Socketsworks across a network as well as locally
Signalsasync notification (SIGINT)
Why is shared memory fastest?

Pipes/sockets/message queues copy data twice through a kernel buffer plus syscall overhead. Shared memory lets processes read/write the SAME physical memory directly with no copying and no kernel mediation — the cost is you handle synchronization yourself.

9. System Calls & Kernel Modes

  • User-mode code can't touch hardware directly — it requests the kernel via a system call (mode switch). Every syscall (fork, exec, open, read, socket, bind) is more expensive than a plain function call.
  • Syscall vs interrupt: syscall = user asks the OS for a service (voluntary, synchronous). Interrupt = hardware signals the CPU (async, involuntary).
  • Kernel types: Monolithic (Linux — everything in kernel, fast, one bug crashes OS) vs Microkernel (QNX, Minix — minimal kernel, stable, slower IPC) vs Hybrid (Windows/macOS).
  • Ring 0 vs Ring 3: kernel mode (full hardware) vs user mode (restricted). The CPU enforces it.

10. Zombie & Orphan Processes

  • Zombie — terminated but exit status not collected by parent via wait()/waitpid(). Occupies a process-table entry.
  • Orphan — parent died first; automatically re-parented to init (PID 1), which reaps it.
Can you kill -9 a zombie?

No — a zombie has already terminated; there's no running code to signal. Only the parent's wait()/waitpid() removes it (or the parent terminates, orphaning it to init).

11. OS Flashcard Essentials

Process vs Thread?

Process = own address space, PCB, heavy context switch, isolated. Thread = shares heap/code/data, own stack+registers, cheap switch.

fork() vs exec()?

fork() copies the current process (child). exec() replaces the process image with a new program. Together = "start a program".

FCFS problem?

Convoy effect — one long job makes all short jobs behind it wait.

How to fix starvation in Priority scheduling?

Aging — gradually increase a waiting process's priority.

Banker's algorithm?

Deadlock avoidance — before granting, simulate whether a safe sequence exists; only grant if safe.

Page fault steps?

Trap to kernel → check validity → invalid=segfault → find frame/evict (dirty→swap) → read page → update page table → restart instruction.

Belady's anomaly?

Only FIFO: adding more frames can INCREASE page faults. LRU/Optimal have the stack property, so they can't.

Fastest IPC?

Shared memory — same RAM mapped into both processes.
