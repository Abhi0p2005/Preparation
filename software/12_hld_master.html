HIGH-LEVEL DESIGN — COMPLETE INTERVIEW GUIDE

Zero to mastery: back-of-envelope estimation, every core building block (load balancers, caching, SQL/NoSQL, consistent hashing, message queues, CAP), a repeatable interview framework, and 10 fully-solved HLD problems.

1. What is HLD & How the Round Works

High-Level Design = designing a distributed system end-to-end: which components exist, how they talk, where data lives, how it scales to millions of users. No class-level detail — think boxes and arrows.

HLDLLD (see page 11)
ScopeWhole system, distributed, at scaleOne module/feature, single process
ArtifactsComponent diagram: clients, LB, services, DBs, queues, CDNClass diagram: classes, interfaces, patterns
Skills testedEstimation, trade-offs, scalability, fault toleranceOOP, SOLID, clean code
The 4S framework — structure every HLD answer with it

① Scenario: what are the features and who uses it? ② Services: what components do we need? ③ Storage: what data, what database, what schema? ④ Scale: how many users/QPS/data — do the math. If you always cover these four, you never miss a requirement.

Typical round format (60 min): 10 min clarify + requirements → 5 min estimation → 20 min high-level diagram → 15 min deep-dive on 1-2 components → 10 min bottlenecks, evolution, trade-offs. Critical rule: never jump to the diagram before requirements and numbers — interviewers explicitly grade that.

2. Back-of-Envelope Estimation

Interviewers want order-of-magnitude math, not exact figures. Round aggressively, show your work aloud.

Latency numbers to memorize (2020s cloud figures)

L1 cache         ~1 ns        Reading 1MB from SSD   ~0.1-1 ms
L2 cache         ~5 ns        Disk seek             ~5-10 ms
RAM access       ~100 ns      Network round trip    ~0.5 ms (DC)
Compress 1KB     ~10 us       1MB over network      ~1-2 ms
Read 1MB RAM     ~10 us       1MB from SSD          ~20 us

Rule of thumb: memory ~100 ns, SSD ~0.1 ms, disk ~10 ms, network within DC ~0.5 ms. If a hot-path read hits disk, that's a red flag — cache it.

Traffic & storage math (walk through this flow)

Assume 100M DAU for Twitter-like app.
QPS estimate:  users that generate a request per day = 10% * 100M = 10M/day
               peak QPS (assume 10% of day is peak) = (10M/0.1)/(24*3600) ~= 11.5K
               peak = 5-10x average = ~100K QPS peak.
Read:write ratio: 100 reads : 1 write is typical for news feeds.
Bandwidth: if each read returns 200KB, reads = 100K * 200KB = 20 GB/s peak.
Storage for 1 year:
   1 tweet = 500 bytes + 200KB media avg -> 10M writes/day * 200KB = 2 TB/day
   = 730 TB/year.  With 3x replication = ~2.2 PB/year.  Add headroom x2.
Estimation formulas to have ready

DAU/day → QPS = (actions * DAU) / 86,400. Peak = 5–10× average. Bytes/day × 365 = storage/year. Throughput × replication factor = actual storage. Bandwidth = QPS × avg payload. Cache size = hot set (usually 20% of data serves 80% of reads).

3. Core Building Blocks

3.1 Client-Server, DNS, CDN

Client-server: browser/mobile (thin clients) → backend over HTTP/HTTPS. DNS resolves example.com → IP: browser checks local cache → ISP resolver → root → TLD → authoritative server. CDN (Content Delivery Network): edge servers cache static content near users; user hits nearest PoP; miss → fetch from origin, then serve + cache. Reduces latency, offloads origin, survives spikes.

Flow diagram (keep this in your head for every problem):

User --DNS--> CDN (static)     \ 
User --HTTPS--> Load Balancer --> App Servers --> Cache --> DB / Queue / Search
                                                          \--> CDN origin (media)

3.2 Load Balancers

L4 (transport)L7 (application)
Looks atIP + port onlyURL/path/headers/cookies
SpeedFaster, less CPUSlower, more features
UseTCP/UDP fan-outPath-based routing, SSL termination, sticky sessions
ExamplesHAProxy(L4), AWS NLBNginx, AWS ALB, Envoy

Algorithms: Round Robin (equal weight), Weighted RR, Least Connections, Least Response Time, IP Hashing (stickiness → session affinity), Consistent Hashing (cache/DB). Health checks: LB pings /health; unhealthy server removed from pool. Sticky vs stateless: prefer stateless app servers (session in Redis) so any request hits any server.

3.3 Caching

Cache the hot set (80/20 rule) in RAM in front of slow sources. Placement: CDN (static edge), client-side, in-memory in app, or dedicated cache tier (Redis/Memcached).

StrategyWriteRisk
Cache Aside (read-through)Write to DB; invalidate cacheCache miss storm after invalidation; stale on crash
Write-ThroughWrite cache + DB togetherExtra write latency; never stale (mostly)
Write-Behind/BackWrite cache, async flush to DBData loss if cache dies
Write-AroundWrite DB only; read cachesCold reads first time

Eviction policies: LRU (most used), LFU, TTL expiry, FIFO. Cache stampede: many requests miss simultaneously and all hit DB — protect with a mutex lock around repopulation or stale-while-revalidate. Consistency: Redis vs DB — use cache-aside with TTL as the pragmatic default; mention write-through when consistency is strict.

3.4 Databases — SQL vs NoSQL

SQL (Postgres/MySQL)NoSQL
ModelRelational tables, joins, ACIDKey-value (Redis), Document (Mongo), Wide-column (Cassandra), Graph (Neo4j)
SchemaFixed, enforcedFlexible
ScaleVertical + read replicas; sharding is painfulHorizontal by design (Cassandra)
Best forTransactions, joins, relational data (payments, orders)High write throughput, flexible schemas, caching, feeds
Strong forConsistency (ACID)Availability + partition tolerance, scale

Replication: single leader (write → leader, reads to replicas), multi-leader (writes anywhere, conflicts), leaderless (write to quorum of N nodes). Read replicas: scale reads; risk: replication lag → read-your-writes problems (route reads after write to leader or add versioning).

Sharding / partitioning: split data by key — hash-based (even distribution, range queries suffer), range-based (hot spot risk), directory-based (lookup table). Shard key choice is the #1 decision: pick a key that distributes writes evenly and keeps related data together (e.g. user_id for feed, order_id). Indexing: B-tree default; covering indexes avoid table lookups; denormalization duplicates data to avoid joins at read time.

3.5 Consistent Hashing

Problem: classic hash(key) % N breaks when N changes (adding a cache server remaps almost every key → cache stampede).

Solution: place servers on a virtual ring (0..2³²-1). A key maps to the first server clockwise after its hash. Adding/removing a server only remaps keys on the arc that shifted — minimal churn.

hash("A") --> 5000  -->  clockwise --> server S2
hash("B") --> 9000  -->  clockwise --> server S1
Ring:  [0 ---- S1(2500) ---- S2(6000) ---- S3(9500) ---- 2^32]
Add S4(4000): only keys between 2500 and 4000 move from S2 to S4.
Virtual nodes (many hashes per server) make distribution uniform.

Where used: cache tier (Memcached), Cassandra partitioning, any distributed hash. Follow-up: "what if a server has more capacity?" → weighted virtual nodes.

3.6 Message Queues & Event Streaming

A queue decouples producers from consumers: producer never blocks on consumer speed; consumers can retry and be added/removed independently. Great for: notifications, order processing, decoupling heavy async work.

Queue (RabbitMQ/SQS)Stream (Kafka)
ModelWork queue, one consumer consumes each msgLog, many consumer groups read independently
OrderingBest effortPer-partition strict order
RetentionDeleted after consumptionReplayable log (retention window)
Fan-outMultiple queuesConsumer groups naturally

Delivery semantics: at-most-once (may drop), at-least-once (may duplicate → make consumers idempotent), exactly-once (hard; dedupe by message ID). Pub/Sub: a topic's events reach every subscriber group (like Observer at system scale). Kafka ordering trick: same partition key (e.g. user_id) ⇒ all events for that user hit the same partition ⇒ ordered.

3.7 API Design

REST: resources + HTTP verbs (GET/POST/PUT/DELETE) + status codes (200, 201, 400, 401, 404, 500). Use plurals: GET /users/42, POST /users. Versioning: /v1/users or header. Pagination: page/limit or cursor-based (stable for feeds — new items don't shift pages). Idempotency: retry-safe writes via Idempotency-Key header → store key + result, return cached result on retry (critical for payments). Rate limiting lives at API layer (see problem R2). GraphQL: client asks for exact fields, one round trip; costs server-side N+1 and caching complexity.

3.8 CAP, ACID, BASE — the consistency trade-off

PropertyMeaning
Consistency (CAP)Every read sees the latest write
Availability (CAP)Every request gets a (possibly stale) response
Partition toleranceSystem keeps working when nodes can't talk
The correct CAP answer (most people get this wrong)

CAP says: under a network partition, you must choose consistency or availability. You do NOT "pick 2 of 3" freely — partitions happen, so P is mandatory; you pick C or A per operation. CP (choose consistency): payments, tickets, orders. AP (choose availability): feeds, likes, notifications, chat presence. Most systems are "CP for money, AP for everything else."

ACID (SQL): Atomicity, Consistency, Isolation, Durability. BASE (NoSQL): Basically Available, Soft state, Eventually consistent. Eventual consistency tools: versioning/vector clocks, read-after-write routing, conflict resolution (last-write-wins or CRDTs).

3.9 Monolith vs Microservices

MonolithMicroservices
DeployOne unitPer-service, independent
ScaleScale whole appScale only hot service
Team velocitySlow at size (merge conflicts)Fast, ownership
CostsSimpleNetwork calls, distributed transactions, observability, ops

Interview stance: start monolith, split when pain appears. Service communication: synchronous (REST/gRPC) vs async (queue). Distributed problems to name-drop: service discovery, circuit breakers (fail fast, degrade), retries with exponential backoff + jitter, distributed tracing (see 3.10). Event-driven microservices: services communicate via events on a stream (Kafka) — loose coupling.

3.10 Observability: Monitoring, Logging, Tracing, Metrics

Metrics — counters/gauges (QPS, latency percentiles, error rate, saturation). Use p99 not average (averages hide outliers). Logging — structured (JSON) with request IDs to correlate. Tracing — one request's journey across services (trace ID → spans): find which service is slow. Dashboards/alerts — alert on symptoms (latency/error rate), not on causes. SLO/SLA/SLI: SLI = measured metric, SLO = target (e.g. 99.9% of requests < 300ms), SLA = contract. Follow-up favorites: "how do you debug a p99 spike?" and "how do you know a service is failing?"

3.11 Security & Reliability Basics

Auth: OAuth2 (authorize 3rd-party access), JWT (stateless signed token), session cookie (stateful). Transport: TLS everywhere. Secrets: never in code/repo — use a vault. Input: validate, never trust client IDs for authorization (IDOR check). Rate limiting on APIs (token bucket) — protection from abuse. DDoS: CDN absorbs, LBs rate-limit, WAF filters. Reliability patterns: retries + backoff, timeouts (avoid cascading), circuit breaker (fail fast), bulkhead (isolate resource pools), graceful degradation (serve stale data instead of erroring), idempotency for retries, graceful shutdown.

4. The HLD Interview Framework (Follow This Every Time)

  1. Clarify & scope (5 min) — features, users, scale hint, constraints. "Is this read-heavy? Does it need realtime? Global or regional?" Write the feature list.
  2. Estimate (5 min) — DAU, QPS (read/write), peak, storage/year, bandwidth. Show the math aloud.
  3. High-level diagram (20 min) — draw the happy path: Client → DNS/CDN → LB → services → storage/queue. Add boxes for each feature; label DBs (SQL/NoSQL + why).
  4. Deep dives (15 min) — interviewer picks a piece: "how do you make feed fast?", "how is data sharded?", "how do you handle duplicate messages?" Use building blocks from section 3.
  5. Bottlenecks & evolution (10 min) — single points of failure (LB, DB leader), what breaks at 10x scale, how to add sharding/caching/queues.
Verbal script that earns marks

"I'll start with a monolith behind an LB; reads go to cache then read replicas, writes to the leader. Media goes to S3 with a CDN. Notifications and processing are pushed onto Kafka so producers don't block. I shard on user_id so a user's feed stays on one node — consistent hashing keeps the churn low. This is AP-consistent for feed, CP for payments." Justify every box.

Common mistakes: starting the diagram too early, ignoring estimation, no read/write split, forgetting CDN/S3 for media, single DB without replication, no failure story, not naming trade-offs, saying "Redis" without saying what's cached or eviction policy.

5. Solved HLD Problems (10)

P1 · URL Shortener (TinyURL)

Requirements: shorten long URL → short key; redirect resolves key → original; custom aliases; analytics optional; global scale; keys must not collide.

Estimation: 100M new/day → writes ≈ 1.1K QPS avg, peak ~5K; read:write = 100:1 → ~110K reads peak. Storage: 100M × 100 bytes/year ≈ 10 GB/year — tiny.

Design:

Client --POST /api/v1/shorten--> LB --> URLService
   URLService: generateKey() -> store (key -> url, created_at) -> return short URL
Client --GET /{key}-------> LB --> RedirectService
   RedirectService: lookup key (cache first, then DB) -> 302 Location: url
Storage: Redis (hot keys, TTL) + Postgres (authoritative, key = PK)

Key generation — the real interview meat: ① Base62: DB auto-increment id → encode to base62 (7 chars ≈ 62⁷ ≈ 3.5×10¹² keys, plenty). Simple, ordered, reversible — but leaks count and needs a distributed ID. ② Random 7-char string + retry on collision (collision probability low at our volume). ③ Distributed ID: Snowflake (timestamp + machine + sequence). Recommendation: base62 on a range from a ticket service, or random with collision retry. Analytics: push click events to Kafka, aggregate in a time-series store.

Bottlenecks & evolution: hot keys (celebrity links) → cache aggressively; DB single point → leader + replicas, then shard by key-hash. Failure story: cache down → reads fall through to DB (still correct, slower).

P2 · Rate Limiter

Requirements: allow N requests per user per window (e.g. 100 req/min); different limits per API/plan; distributed across many API servers; low latency.

Algorithms:

AlgorithmHowTrade-off
Token BucketBucket refills at rate r, capacity b; take token per requestAllows bursts; simple — default choice
Fixed WindowCounter resets each minute2x spike at boundary (59th sec + 00th sec)
Sliding Window LogStore timestamps, count in last 60sPrecise, memory-heavy
Sliding Window CounterWeighted previous + current windowGood balance — most used in practice
Pseudo (Token Bucket, Redis):
  bucket = GET rate:user:{id}            // {tokens, lastRefill}
  tokens = min(capacity, tokens + (now-lastRefill) * rate)
  if tokens >= 1: SET bucket; return ALLOW
  else: return 429 Too Many Requests

Distributed design: Redis is the shared counter store (atomic INCR + EXPIRE for fixed window, Lua script for token bucket). API servers call Redis (2-3 ms) — fast enough. Responses: 429 + Retry-After header. Placement: edge (API gateway / LB) so blocked traffic never reaches app servers. Failure story: if Redis is down, fail open (allow) or closed (reject) — pick fail-open with a secondary local in-memory limiter to avoid self-DoS.

P3 · Twitter / News Feed

Requirements: post tweet, follow users, home timeline = reverse-chronological merged feed of followed users; like/comment; 100M DAU; 100:1 read:write.

Estimation: writes ≈ 10M tweets/day → ~115 avg QPS, ~1K peak. Reads ≈ 100K QPS peak. Feed size: each home timeline = 10 × avg daily tweets per followed account. Storage: ~2 TB/day with media → ~730 TB/year → S3 + CDN for media, Postgres/Cassandra for metadata.

Design — the classic choice: push vs pull (fan-out)

Option A: PULL (fan-out on read)
  HomeTimeline read: SELECT tweets WHERE user_id IN (followees) ORDER BY ts DESC LIMIT 20
  Simple, no extra storage; but every read scans followees x tweets -> slow at 100K QPS.
Option B: PUSH (fan-out on write) — Twitter's approach for normal users
  On tweet: for each follower, append tweet_id to follower's timeline cache (Redis list, cap 800).
  Read: GET home:{user} -> list of tweet_ids -> fetch tweets (cached) -> render.
  Problem: celebrity with 100M followers -> 100M cache writes per tweet = "fan-out problem".
Fix: hybrid — celebrities (high follower count) use PULL; normal users use PUSH.
Read path: merge precomputed list + celebrity timeline pulled on read.

Write path: TweetService -> validate -> store (tweet_id, user_id, ts, content)
   -> media to S3 -> push to followers' timelines (async via Kafka) -> fan-out via workers.
Read path: TimelineService -> read home:{user} -> hydrate tweet content from cache/DB -> return.

Storage: tweets in Postgres or Cassandra (shard by user_id; keep a user's tweets on one node for easy pull). Timeline cache in Redis (list of ids). Likes/comments: separate counters (Redis) + detail store; update asynchronously. Ranking upgrade: swap reverse-chron for a scored/ML feed — mention as evolution. Failure story: fan-out worker lags → timeline shows stale items; mitigate with pull fallback for new tweets.

P4 · Chat / Messaging (WhatsApp)

Requirements: 1:1 + group chat; message delivery, read receipts; push notifications; ordering per conversation; offline messages; media; 100M+ DAU.

Estimation: avg 40 msgs/day/user → ~40M msgs/day → 460 avg QPS, ~4.6K peak. Each msg ~500 bytes → ~20 GB/day → ~7 TB/year. Media (photos/videos) → S3. Retention: keep "last seen" and recent messages hot; archive older.

Design:

App --WebSocket--> ChatService (L7 LB keeps sticky connection) 
   ChatService validates -> saves msg -> determines recipients (group membership via MembershipService)
   -> push via NotificationService (APNS/FCM) for offline users -> append to recipient's inbox
Recipient online: realtime path via WebSocket (long-lived connection to their server)
Recipient offline: msg stored in inbox; delivered on next connect (or via push)
Consistency: conversation log stored in Cassandra; each participant reads their own copy
Group chat: Kafka fan-out (one write per group -> consumers push per member)

Ordering: per-conversation sequence numbers; client shows them and reorders. Duplicate/inflight messages (network retry) → dedupe by client-generated message ID. WebSocket scale: LB sticky sessions + a gateway per connection; chat state (connection → user) in Redis so any node can find the user's connection. Read receipts: user → "read" event → Kafka → notify sender (only delivery status needs realtime). Media: client uploads to S3 directly (pre-signed URL), sends the reference in the message. Failure story: chat server dies → WS reconnects via LB to another node; offline messages pick up from inbox on reconnect.

P5 · Uber / Ride Sharing

Requirements: riders request rides; find nearby drivers; match + dispatch; live driver location; ride lifecycle + payments; realtime at scale.

Estimation: 10M DAU riders, 1M concurrent drivers. Location updates: each driver 4-5 updates/sec → 5M updates/sec writes to a geo store (this is the hard part — not SQL friendly). Ride requests: ~1K QPS peak.

Design:

Driver app --HTTPS/WS--> LocationIngestionService --> Kafka (driver position stream)
   -> GeoSpatial store (GeoHash index: R-tree / PostGIS / Redis GEO) -> keeps live positions
Rider app --POST /v1/ride--> RideService -> findDrivers(radius) [GeoHash lookup -> candidates]
   -> RankingService (distance, rating, surge) -> dispatch -> driver accepts -> ride begins
RideService -> on accept: create Ride (CP: money!) -> status transitions via State machine
Match is "CP-ish" (one driver can't take two rides) -> use a lock on driver: Redis SETNX
Payments: separate PaymentService (CP, exactly-once via idempotency key)

GeoHash: encode lat/lng to a string; prefixes = rectangles. Query: get geohash of rider + 8 neighbors → candidate driver ids → refine with exact distance. As driver moves, hash changes and they're re-indexed (partition by hash prefix for scale). Realtime push: drivers get ride offers via WebSocket; rides use fire-and-forget push + push-notification fallback. Surge pricing: compute demand/supply ratio per geohash → multiplier (Strategy/service). Duplicate dispatch risk: broadcast offer to multiple drivers, first-accept wins via atomic Redis key. Failure story: geostream backlog → stale driver positions; mitigate with TTL on positions and "last seen" timestamps.

P6 · Video Streaming (Netflix/YouTube)

Requirements: upload, encode, catalog, search, stream video with smooth playback, recommendations; global CDN.

Estimation: 200M subscribers; peak streaming ~ millions concurrent; each stream needs steady bitrate — bandwidth dominated by CDN egress, not your servers. Hot catalog: 20% of titles = 80% of views → those live fully on CDN.

Design — the pipeline:

Upload: Creator --PUT--> UploadService --> Object Store (raw)
Encode: encoder workers pull raw -> transcode into multiple bitrates (240p..4K) & HLS segments
        (2-10s chunks) -> store in CDN origin -> manifest (.m3u8) references all variants
Playback: Player --GET manifest--> CDN edge (near user) -> ABR: adapt bitrate by bandwidth
Discovery: Search (Elasticsearch) + Recommendations (offline ML pipeline, cached)

Adaptive Bitrate (ABR): player watches buffer + bandwidth, requests higher/lower quality segment — why streaming doesn't buffer. CDN strategy: edge cache popular titles (pre-populate "top 100"), miss → fetch from origin, long-tail served direct. Why not one giant DB: video metadata (title, cast) is relational but tiny; play metrics are high-write → time-series/analytics store. Upload pipeline asynchrony: encode is slow (min) → decouple with a queue; notify creator when ready. Failure story: CDN region outage → route to secondary CDN or origin; encoder cluster backlog → scale workers, upload still accepted. Keywords to drop: HLS/DASH, ABR, transcoding matrix, egress cost optimization.

P7 · E-commerce Checkout (Amazon)

Requirements: product catalog, cart, checkout with inventory check, payments, order status, notifications; money flows must be correct (CP).

Estimation: 300M customers; orders peak on sale days (10x normal); each order → cart→inventory→payment→order-record→notify pipeline.

Design — order state machine:

CartService (Redis cart) -> CheckoutService (validate stock, compute total)
   -> Reserve inventory (atomic decrement; CP) -> PaymentService (idempotency key, exactly-once)
   -> On success: create Order (state PLACED) -> push to Kafka -> downstream
Order states: PLACED -> PAID -> PACKED -> SHIPPED -> DELIVERED; CANCELLED/REFUNDED
Inventory: "reserve" decrements available count; expires reservation after 15 min (like seat lock)
Search: product catalog in Elasticsearch (fuzzy, facets); product details in cache + DB

Correctness under concurrency: last item + two buyers → optimistic lock on inventory row or atomic UPDATE inventory SET qty=qty-1 WHERE id=? AND qty>0 (check rows affected). Exactly-once payment: client sends idempotency key; PaymentService dedupes retries; never double charge. Order read path: order history = read replicas; order detail cached. Peak (sale day) strategy: queue the entire checkout flow so the web tier stays responsive; push notifications async. Failure stories: payment timeout → mark PENDING + reconcile job; inventory oversold on a shard → consistency job reconciles. CP vs AP split: payments/orders/inventory = CP; recommendations/cart sync = AP. Sharding: order_id-hash shards for writes; user_id for order-history reads (dual-key or denormalized copies).

P8 · Cloud Storage / File Sync (Google Drive)

Requirements: upload/download files, sync across devices, sharing/ACLs, versioning, dedup, large files (chunking), offline conflicts.

Estimation: 1B users; free tier 15GB; assume avg 100 MB/user active storage → petabytes; uploads async (files are big, latency-tolerant). Metadata (file → chunks map, ACLs) is small and relational — separate from blobs.

Design:

Client --PUT (pre-signed URL)--> Object Store (S3) for blob; chunked multipart for big files
   Metadata: FilesService (Postgres/Cassandra): file_id, owner, ACLs, chunk list, version
   Sync engine: watch local changes -> upload new chunks -> commit new version metadata
Sharing: share file_id with user_id + permission (view/edit) -> ACL check on every access
Dedup: hash each chunk (SHA-256); only upload chunks not already stored (cross-user dedup)
Versioning: metadata rows per version; keep last N, GC old blobs (LCS/lifecycle policies)
Conflict: last-write-wins or fork on edit (like Drive's "conflict copies")

Chunking: split into e.g. 8MB chunks; parallel upload resume; only changed chunks re-uploaded on edit → cheap sync. ACL check: authn/authz service in front of every metadata read; permission lookup cached, revoked via push-invalidation. Scale: metadata shard by file_id; blob in S3 (which is already replicated). Failure story: interrupted upload → resume from last chunk (idempotent chunk PUTs with hashes); replica region failover for S3 is automatic. Interview differentiator: mention content-addressed storage + chunk dedup explicitly.

P9 · Notification System

Requirements: send push (APNS/FCM), email, SMS; templated; per-user preferences; millions of notifications/day; retries + backpressure.

Estimation: 100M DAU; 10 notifications/user/day → 1B/day → ~11.5K avg QPS, ~100K peak around events. Each send is async (no need to block request thread).

Design:

Producer (any service) --POST /notify--> NotificationService -> validate -> store notification
   -> route to Kafka topics: push/email/sms  -> consumers per channel
PushWorker: batch device tokens (FCM/APNS limits) -> send -> retry with backoff on failure
EmailWorker: template (Mustache) + send via SES/SendGrid (dedupe, DKIM)
SMSWorker: rate-limit (carrier limits) + send
UserPreferenceService: channel opt-out check BEFORE enqueueing (or filter in consumer)
Store: recent notifications (Redis) + history (Cassandra, TTL); unread count

Key challenges: ① Backpressure — third parties (FCM) throttle; use queues + retry with exponential backoff and dead-letter queue for permanent failures. ② Idempotency — same notification shouldn't double-send; dedupe by (user, type, entity_id). ③ Ordering — per-user ordering via partition key user_id if sequence matters (usually doesn't for notifications). ④ Fan-out — one event → 10M pushes: push per-user messages onto Kafka, consumers scale horizontally. ⑤ Dead-letter queue: poison messages go to DLQ for inspection, don't block the queue. Failure story: provider outage → circuit breaker on the provider, queue backlog grows, replay after recovery.

P10 · Search Autocomplete (Typeahead)

Requirements: return top-K suggestions as user types, prefix-based, ranked by frequency/recency, fast (<100ms), global scale.

Estimation: 500M daily queries; ~20 keystrokes/query → 10B keystrokes/day → ~115K QPS avg, >1M peak (autocomplete traffic is heavy). Suggestion lookup must be pure cache/memory (no DB on hot path).

Design — the two paths:

WRITE path (offline): collect search logs (Kafka) -> Aggregator (hourly/daily)
   -> build trie with counts -> filter (profanity, PII) -> snapshot to storage
   -> periodically reload in-memory trie per server / precompute top-K per prefix
READ path (online): GET /suggest?q="ap" -> server's in-memory trie
   -> traverse "ap" node -> return top 10 by count -> cache in Redis, TTL
   -> client-side debounce (150ms) + prefix caching (cache "ap" suggests for "app")

Trie vs alternatives: in-memory trie (prefix → top-K ranked suggestions precomputed at each node) is O(len) lookup, memory-heavy → use a compact trie / a map of every prefix → top-K list ("prefix → ranked list" map). Ranking: frequency × recency weight; personalization (user location/history) as an optional second pass. Scale: replicate the in-memory snapshot across many stateless servers behind LB — reads are pure memory, hit rates near 100%. Failure story: server reboots → reload trie from storage snapshot (lazy-load + async refresh); data freshness is eventually consistent (hourly), acceptable. Extra marks: keyboard-layout correction, language detection, storing only top-K per prefix to bound memory.

6. Trade-off & Mistake Cheat-Sheet

DecisionTrade-off to verbalize
SQL vs NoSQLSQL = joins + ACID, vertical scale; NoSQL = horizontal write scale + flexible schema, sacrifices consistency/complex queries.
Push vs Pull feedPush = fast reads, expensive writes (celebrity problem); Pull = cheap writes, slow reads; hybrid = best of both.
Cache before vs after DBCache-aside default; write-through when consistency strict; never cache money without TTL + invalidation.
Queue vs direct callQueue = decoupled, retryable, slow-safe; direct = simpler, synchronous failure handling.
Shard keyUniform writes vs co-located reads — can't always have both; document the loser.
At-least-once vs exactly-onceAt-least-once + idempotent consumers is the practical default; exactly-once is expensive.
Monolith vs microservicesStart monolithic; split by bounded context when teams/scale demand it.
Strong vs eventual consistencyStrong = simple, slow/limited; eventual = fast/high-availability, needs conflict handling.

7. HLD Quick Revision Flashcards

What is the 4S framework?

Scenario (features), Services (components), Storage (data + DB choice), Scale (numbers). Cover all four in every problem.

Latency order-of-magnitude: memory, SSD, disk, DC network?

RAM ~100 ns, SSD ~0.1 ms, disk ~10 ms, network within a datacenter ~0.5 ms. Hot paths must not touch disk.

How do you convert DAU to QPS?

(actions per day × DAU) / 86,400 ≈ average QPS; peak = 5–10× average. 1M requests/day ≈ 12 QPS average.

L4 vs L7 load balancer?

L4 routes on IP:port only (faster). L7 inspects URL/headers/cookies (routing, SSL, sticky sessions).

Cache-aside vs write-through?

Cache-aside: read DB→populate cache, write DB→invalidate (default, can be stale). Write-through: write both synchronously (consistent, slower writes).

Why consistent hashing instead of mod N?

mod N remaps nearly all keys when N changes → cache stampede. Consistent hashing only remaps keys on the affected ring arc; virtual nodes fix skew.

When do you choose Cassandra over Postgres?

Huge write throughput, horizontal scale, flexible schema, when queries are key-based (no joins). Choose Postgres when joins/ACID/relational integrity matter.

What does CAP actually say?

Under a network partition you choose consistency OR availability (P is unavoidable). Money = CP, feeds/notifications = AP.

How do you guarantee message ordering in Kafka?

Same partition key (e.g. user_id) routes all of a user's events to one partition, preserving order within it.

How do you handle duplicate messages/retries?

Idempotent consumers + dedupe by message/client request ID; retries with exponential backoff + jitter; dead-letter queue for poison messages.

How do you make a feed of a celebrity fast?

Hybrid fan-out: normal users get push (precomputed timeline); celebrities with millions of followers use pull (merged on read) to avoid 100M cache writes per tweet.

What's the single biggest throughput bottleneck in Uber-style systems?

Driver location writes (~5M/s). Solved with geo-indexing (GeoHash/R-tree) on a stream pipeline — not a SQL table.

Why chunk files and dedupe by hash in Google Drive?

Chunks enable resume + parallel upload; hash dedup means edits only re-upload changed chunks (cheap sync) and identical chunks stored once.

Where does rate limiting live and what store?

Edge (API gateway/LB) using Redis (atomic counters / token bucket Lua). Fail-open if Redis is down but add a local limiter to avoid self-DoS.

Interview golden rule for HLD?

Requirements → estimation → diagram → deep-dive → bottlenecks, always justifying each box with a named trade-off.
